# CUDA Runtime Layer

## Validation status

The Milestone 3 implementation is **CUDA compile-validated, not GPU
runtime-validated**. Commit `ebb3585` compiled with NVCC 12.6.85 and GCC 13.2 in
the ARM64 `nvidia/cuda:12.6.3-devel-ubuntu24.04` container with warnings as errors.
All 49 hardware-independent tests passed in that CUDA-on build. Six GPU tests were
built and then skipped because the container had no NVIDIA driver/device.

As later subsystems were added, the macOS CPU-only Debug, Release, and ASan/UBSan
configurations reached 186 passing tests. The current CUDA-on build passes 185
hardware-independent tests and registers 61 GPU tests (246 total), all skipped
without a device; its container omits the separate Python converter test. CUDA
correctness, resource-leak, and timing behavior remains pending a physical NVIDIA
GPU.

## Error handling

`HELIX_CUDA_CHECK` and `HELIX_CUDA_CHECK_CONTEXT` evaluate a CUDA expression once
and preserve:

- the failed expression,
- CUDA error name and description,
- operation context such as byte count/device/direction,
- source file, line, and function through `helix::Error`.

`cudaErrorMemoryAllocation` maps to `ErrorCode::kResourceExhausted`; other CUDA
failures currently map to `ErrorCode::kRuntime`. Cleanup paths cannot throw, so
destructor failures go through the logging sink with their operation context.

## Device ownership

`helix::cuda::DeviceGuard` records the current CUDA device, selects the requested
device for a lexical scope, and restores the prior device in its destructor. It is
non-copyable and non-movable because moving a scope guard obscures restoration
order.

Streams, events, and buffers remember the device on which they were created. Their
operations establish that device with a guard, and cross-device stream/event use is
rejected at the host boundary. Destruction attempts to select the owning device,
release the resource, and restore the caller's prior device without throwing.

## Streams and events

`helix::cuda::Stream` is a move-only owner of a non-default CUDA stream. The
default creation mode uses `cudaStreamNonBlocking`; a priority constructor is also
available. It supports completion queries, synchronization, and event waits.

`helix::cuda::Event` is a move-only owner supporting record, query, and
synchronization. `elapsed_time_ms` rejects events created with
`cudaEventDisableTiming`, requires both events on one device, and delegates timing
to `cudaEventElapsedTime`. Callers must record events around warmed-up work on the
same stream when producing benchmark results.

Moved-from stream/event handles are explicitly rejected rather than accidentally
being interpreted as CUDA's default stream or an invalid runtime handle.

## Memory and tensor integration

`helix::cuda::Buffer` currently owns a direct `cudaMalloc` allocation and releases
it with `cudaFree`. It exists as the correct baseline before `HelixAllocator`
replaces per-allocation runtime calls.

The memory API provides checked synchronous and stream-ordered asynchronous H2D,
D2H, D2D, peer-copy, and memset operations. Asynchronous copies accept ordinary
host pointers for correctness, but actual host/device overlap generally requires
pinned host memory; pinned staging is deferred to the overlap milestone.

Tensor `Storage` is backend-aware:

- CPU allocations use aligned C++ allocation/deallocation.
- CUDA allocations use direct checked runtime allocation in CUDA builds.
- the requested alignment is verified against the returned CUDA pointer.
- storage retains its device so cleanup uses the correct context.

`Tensor::to`, `clone`, `copy_from`, `zeros`, `from_values`, and deterministic random
construction have CUDA paths. Random values are generated by the deterministic CPU
initializer and transferred; no host code dereferences a device pointer. Same-GPU
copies use D2D copies, and different-GPU transfers use `cudaMemcpyPeer`.

## Synchronization contract

Synchronous Tensor operations use synchronous CUDA copies/memset. The lower-level
asynchronous memory functions enqueue work on a caller-owned `Stream`; the caller
must keep source/destination memory alive until the stream/event dependency proves
completion. M8 now provides a separate CUDA-event-backed
`StreamOrderedAllocator`, but Tensor storage still allocates directly because it
does not record every stream that used a block. A caller using the allocator must
order all such uses before the event on the chosen release stream. Every CUDA
Tensor storage allocation is therefore still directly freed and `cudaFree` may
synchronize.

The current runtime objects are safe to move between host threads only when no
other thread concurrently accesses the same object and the CUDA context rules are
respected. They contain no internal mutex. Independent objects may be used from
independent threads.

## Validation commands

With an installed toolkit:

```bash
./scripts/run_cuda_validation.sh
```

For compile-only CI, `.github/workflows/cuda-compile.yml` builds CUDA sources and
runs only tests not labeled `gpu`. A GPU host should additionally run:

```bash
ctest --test-dir build-cuda -L gpu --output-on-failure
compute-sanitizer --tool memcheck ./build-cuda/tests/helix_cuda_runtime_tests
```

## Known limitations

- No GPU runtime test has run in the current environment.
- No pinned host allocator exists yet.
- The allocator cache is not integrated with Tensor because multi-stream storage-use
  tracking is not implemented yet; its event adapter is compile-only validated.
- Tensor transfers are synchronous at the high-level API.
- Peer copies require runtime/driver support and have not been hardware-validated.
- Destructor failures can only be logged; callers needing explicit cleanup status
  should synchronize before resource destruction.
